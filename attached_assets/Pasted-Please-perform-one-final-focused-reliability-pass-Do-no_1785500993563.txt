## Priority 1: prevent duplicate task creation in local state

Review:

```text
artifacts/pmt-app/src/App.jsx
```

The current `persistTaskCreate()`:

1. calls Firebase `set()`;
2. waits for it to resolve;
3. manually prepends the created task into `clientLogs`.

Firebase’s local listener may already add the task before the `set()` promise resolves. The manual insertion can therefore create a duplicate local task.

Use only one local-state source.

Preferred implementation:

```js
const persistTaskCreate = useCallback(
  async (clientId, taskData) => {
    if (!firebaseUser) {
      throw new Error(
        'No authenticated user — cannot create task'
      );
    }

    const newRef = push(
      ref(db, `clientLogs/${clientId}`)
    );

    const pushKey = newRef.key;

    const task = sanitizeForFirebase({
      ...taskData,
      id: pushKey,
      taskKey: pushKey,
    });

    await set(newRef, task);

    // Do not manually insert into clientLogs here.
    // The Firebase listener is the authoritative local-state update.
    return {
      ...taskData,
      id: pushKey,
      taskKey: pushKey,
    };
  },
  [firebaseUser]
);
```

Alternatively, perform an optimistic insertion before the write, but then:

* deduplicate by `taskKey`;
* do not insert again after success;
* remove the optimistic record if Firebase rejects the write.

Add tests covering:

1. Firebase listener adds the task before `set()` resolves.
2. Firebase listener adds the task after `set()` resolves.
3. The final local task collection contains exactly one task with the push key.
4. A failed creation does not leave an unsaved task visible.

## Priority 2: roll back failed compatibility writes

`persistClientLogs()` currently applies `finalLogs` locally before Firebase confirms the root multi-path update.

When Firebase rejects the update, it shows an error but leaves the unsaved local state visible.

Change `persistClientLogs()` so failed writes restore the previous local state.

Suggested behaviour:

```js
const persistClientLogs = async nextLogsInput => {
  const previousLogs = clientLogsRef.current;

  const {
    multiPathUpdate,
    finalLogs,
  } = computeClientLogsDiff(
    previousLogs,
    nextLogsInput,
    generateTaskKey
  );

  clientLogsRef.current = finalLogs;
  setClientLogs(finalLogs);

  if (!Object.keys(multiPathUpdate).length) {
    return;
  }

  try {
    await update(ref(db), multiPathUpdate);
  } catch (error) {
    clientLogsRef.current = previousLogs;
    setClientLogs(previousLogs);

    setSaveError({
      message:
        'Could not save changes. The change was reverted.',
      time: Date.now(),
    });

    throw error;
  }
};
```

Consider concurrent local actions carefully. A simple full-state rollback can itself remove a later successful user action.

A safer approach is:

* store the failed update plan;
* reverse only the paths affected by that plan; or
* prevent another compatibility mutation while one is pending.

Choose the simplest correct approach and document it.

Do not leave a failed change displayed as saved.
